# Windows port: status and how it works (32-bit x86, Direct3D 11)

## Build / run (PowerShell, from the project root; needs Visual Studio Build Tools and `pip install ziglang`)
```
python port\collect_nonmatching.py     # gather behaviour-level C for functions that are not matching C yet -> port\nonmatching
python port\build_clang.py [--all]     # game C -> clang -> LLVM IR -> big-endian rewrite (port\be_ir.py) -> port\build\obj_c
powershell port\relink.ps1             # link (generates port\gen\syms.asm / stubs.c / fnptrs.c from the unresolved list)
powershell port\run.ps1 -Seconds 10    # run the newest build, print the log and a symbolized crash/trace
powershell port\screenshot.ps1         # capture the window
```
The ROM is read from `baserom.us.v11.z64` in the working directory (never committed).

## Design
- **Addresses.** Game globals are absolute symbols (`port\gen\syms.asm`) at their original addresses, so guest address == host
  address.  8 MB at 0x80000000 is the guest RAM; overlay A's data tail is at 0x400000; low code space 0x200000 is reserved.
  If the host already uses one of those ranges the exe relaunches itself (new ASLR layout).
- **Byte order.** The ROM and all its data are big-endian.  `port/be_ir.py` rewrites every 16/32/64-bit integer, pointer, float and
  double load/store in the compiled game code into a byte-swapped access, so the C source needs no changes and data/assets are
  kept exactly as in the ROM.  Objects defined inside a module (private tables) stay native.  `va_arg` is special-cased in
  `port\compat_clang.h`; the OS shim uses `LD32/ST32...` for every guest field it touches.
- **Code pointers** stored in data tables are relocated at load time (`port\gen\fnptrs.c`: guest address -> host function).
- **libultra** is replaced by `port\os_shim.c`: baton-scheduled threads (one runs at a time, priority based), message queues in
  the game's own OSMesgQueue structures, timers, VI/SP/DP/PI events, PI DMA from the ROM, a keyboard controller.
- **TLB demand paging.** The game pages assets in through TLB misses.  Asset space is moved to 0x30000000+ (overrides of
  `func_0023CDC4` / `func_0023CCC4`) and an access-violation handler loads the faulting 4 KB page from the ROM (`page_in`).
- **Drafts.** Functions without matching C use the workers' best drafts (`port\nonmatching`, hand fixes in `port\overrides`).
  They are behaviour-level only and are the main source of bring-up bugs.
- **Debugging.** `-finstrument-functions` feeds a ring buffer of function entries; a crash prints the last calls
  (`python port\where.py` turns RVAs into names).

## Status (latest, 2026-10-09)
The port boots through the game's own boot sequence, menus, loadout and match options into 1-player trials and 2-player split-screen
matches with music and sound effects (libultra audio library + `port/audio_hle.c`), renders them through the D3D11 F3DEX2 renderer
(`port/renderer.cpp`) and runs the attract mode indefinitely (seven demo screens, then recorded gameplay demos).  Scripted runs
(`port/pressfile.ps1 -Speed 10`, clock-scaled `TUROK_SPEED`) cover boot -> level, 2-player and 4-player matches through the results screen; the sections below are the chronological log
of how each piece was brought up and which traps were found.  Older paragraphs describe the state at their date, not today.

How the missing code is covered
- **Exact static recompilation** (`port/mips2c.py`, `gen_recomp.py`): every function without matching C is recompiled from the ROM's
  MIPS code (integer + FPU subset, jump tables, o32 float ABI via `fpsig.py`, 64-bit helper adapters, odd-register 64-bit FPU
  saves).  ~800 functions; validated against the matching C by differential tests (`gen_difftest.py`, 1221/1226 agree).
  Drafts in `port/nonmatching` are only the fallback when recompilation fails.
- **Entry points inside functions** (`port/forced_entries.txt`, `port/game_glue.c` aliases): some code pointers land a few bytes
  into a function or on a bare `jr $ra`; those are handled by alias stubs / an exec-fault redirect.

Debug switches (environment variables): `TUROK_SKIPMENU=1` (leave the controller-pak screen), `TUROK_AUTOPRESS=1`,
`TUROK_FTRACE=func_x,bt,dump (function arg trace; TUROK_TRACE is the oracle frame trace)`, `TUROK_WATCH=<guest word>`, `TUROK_SAMPLE=1`, `TUROK_DLFRAME=n` (dump display lists),
`TUROK_VTXLOG=1`, `TUROK_NOTRI`, `TUROK_NORECT`, `TUROK_DUMPTICK=1`.

### Lead on the garbled loadout models
- The 32x64 CI8 model textures (display list: `FD500000 801D4050` image, `FD100000 801D4070` palette) decode as noise because the image address overlaps the palette: RAM at 0x801D4040.. shows chunk headers (`00000001 00000010 ...`) where the image should be. The model resource is not laid out the way the display list builder assumes, so suspect the loader/unpacker of that resource type (pointer fix-up or chunk unpack in recompiled code). Dump the area with `port_dumpnow.txt` (writes port_mem.bin / port_mem2.bin).
- `TUROK_TEXDUMPWH=32x64` dumps decoded textures of one size to port/build/tex_N.ppm.
- Allocation trail for that resource: `alloc size=3360 -> 801D0C90` (flags=0) is followed by a run of `alloc size=70 -> 801D4010, 801D40A0, ...` (0x90 apart), each next to an RNC1 asset (header `RNC 01`, unpacked size 0xA40) that unpacks into a temporary buffer at 80474320. The display list's image pointer 801D4050 lands just past the 0x3360 block, i.e. inside one of the 0x70 blocks - the unpacked size / allocation size used for these model blocks looks wrong (or the unpacker writes more than was allocated). Start with the function that issues the `alloc size=3360` (see the log lines before it) and the RNC unpack call that follows.

### Resolved: garbled loadout models
- Cause: matching C declared `func_0028FDD8` as `void` although the original leaves the piece size in v0 and recompiled callers (`func_00295B90`, ...) use it; models were allocated 0x70 bytes instead of 0xA40. Fixed by `port/overrides/func_0028FDD8.c` returning the size.
- Same class of bug may exist elsewhere: matching-C functions typed `void` whose result lingers in v0. Symptom: a recompiled caller computes with garbage after the call. Fix by overriding the function with a returning prototype.

### Audio (2026-10-09)
- The real libultra audio library runs (alInit/alSynNew/alAudioFrame, sequence player, sound player, reverb). Its ABI1 command lists are executed by `port/audio_hle.c`; `port/audio_out.c` plays the pushed AI buffers through waveOut. Music and the menu play cleanly; `TUROK_WAVDUMP=file.wav` records the stream for offline analysis (python: discontinuities, clipping, per-channel smoothness), which found every bug below.
- Semantics verified against the game's own command streams: ADPCM writes its 16-sample history in front of the decoded frames (RESAMPLE reads at out+32); RESAMPLE uses the 64-phase microcode table on the 4 samples before the position; INTERLEAVE's count is one channel's byte length; ENVMIXER keeps an 80-byte state with exponential ramps; POLEF is the reverb's two-pole filter. Debug: `TUROK_HLELOG=start;count` (command lists), `TUROK_HLEDUMP=list` (DMEM after each stage), `TUROK_VOLOPT=mmss` (option bytes; a blank EEPROM leaves the music volume at 0, so 0x80/0x80 are defaulted), `TUROK_RS`, `TUROK_NOPOLEF`, `TUROK_NOWET`.
- Recompiler: the game sets Status.FR (osCreateThread: SR=0x0400FF03), i.e. 32 separate 64-bit FPU registers; doubles appear in odd registers (`_getRate`). `g_fpr` is 32 x 2 words, `gd/sd/ldc1/sdc1` move whole registers (4-byte accesses only - `be_ir` would swap an 8-byte access as one unit).
- Pitfall: removing a `port/overrides/X.c` whose original lives in `src/` leaves X as an UNIMPLEMENTED stub until the src file is rebuilt (touch it); `alCSPSetVol` went missing that way and the music played at the library default volume 0x7FFF (clipping).
- Fast-forward: `TUROK_FF=1` runs the game at full host speed (10 frames per presented frame, audio muted) until the title screen (29); `TUROK_FF=a;b;c` alternates: fast until screen a, normal until b, fast until c (an even count ends fast for good, e.g. `29;10` = normal through the menus, 10x inside a level); holding Tab fast-forwards at any time. `pressfile.ps1 -Boot <s>` is the wait before the Start taps (2 s automatically under TUROK_FF).

### Dropped argument registers (2026-10-09)
- Root cause of the attract-demo crash and of a whole class of garbage-pointer faults: a matching C decomp can declare fewer parameters than the function really takes, because the MIPS code is identical whether a register was "passed" or just left alone. `func_002171FC(actor, state)` calls `state->fn110()` with no arguments, but its callers (func_0028CCB8, the recompiled func_00266830) pass a third one - a scratch buffer - which the MIPS code leaves in a2 for the handler `func_00219A40(Plr *, u8 *, f32 *)`. On x86 the handler read a stack word instead and dereferenced it. The same pattern (`func_0024795C(&qo)` instead of `func_0024795C(&qo, o)`, `func_00442158()` instead of `func_00442158(item)`, trampolines like `func_002A1E8C(void)` that pass a0..a3 and v0 straight through) was behind the level crash after firing and several of the earlier null guards.
- Tools: `python port/argscan.py` lists C call sites that pass fewer register arguments than the callee reads (recompiled callees: registers read before written in `port/native/recomp`, transitively through pass-through calls; C callees: declared parameters; uses `port/build/turok.map` to know which object is linked). `python port/passthru.py` checks each flagged site against the caller's MIPS code (`port/build/asm_func`): if the missing register was never written before the jal (and no earlier call clobbered it) the N64 passed the caller's own incoming argument, i.e. the original source forwarded it. `python port/passthru_fix.py --diff|--write` generates overrides for those: it maps the caller's parameters to argument registers (hidden struct-return pointer in a0, by-value Vec3f/Quat4, leading floats in f12/f14), widens the parameter list with `u32 pt_aK`, appends the arguments at the call and widens the callee's local prototype. `python port/jalrscan.py` does the same survey for C function-pointer calls (targets unknown, so those are hand-written overrides that forward the live registers through a cast).
- Result: 72 generated plus 28 hand-written overrides (`port/overrides`, headers say which tool). Iterating scan -> fix -> scan reaches a fixed point with 0 pass-through sites left; the remaining ~140 flagged sites are "garbage on both machines" (the register was clobbered before the call on the N64 too, so the callee cannot depend on it). Not modelled: float arguments in f12/f14 for C callees (one manual case, func_00284844 -> func_002745D4(x)) and by-value structs of unknown size.
- Verification: attract demo 7 cycles under 10x without a crash (it used to fault in the 2nd cycle at normal speed, run_demo1.log, and after 6-11 cycles under FF); 1-player level with firing and walking clean (lv6_*.png); the earlier "crash after firing" in lv5 was `func_0024795C(&qo)` reading a stack word as its object pointer - the new overrides had merely changed which garbage was there.

### Crash reporting, post-demo renderer fault (2026-10-09)
- Every demo soak "ended" quietly after the 7th attract cycle: run.log stopped at `screen id -> 2` / `game state st=20` and the process was gone. It was a crash on the main thread (renderer) that no handler reported: the game-thread `__except` only covers the game thread, and the one-shot vectored report had already been consumed by a first-chance fault (an `IsBadReadPtr` probe inside the handler itself). `crash_filter2` now writes a raw report first (`CRASH(raw): code rva acc addr tid registers` plus up to 160 return addresses into the module, via WriteFile on the log handle - `_get_osfhandle(_fileno(stderr))`, a GUI process has no fd 2) for the first 6 access violations, then the old fprintf report once. `port_early.txt` keeps the same raw line for every exception, including first-chance ones. Symbolise rvas against `port/build/turok.map` (Rva+Base column minus 0x20000000; lowercase hex). `TUROK_CRASHTEST=1` faults on purpose at frame 300 to check the path.
- The fault: `loadTile` with lrs < uls (a LoadTile command the game issues while tearing the demo down) gave a negative row size, which memcpy took as ~4 GB and wrote past the heap. The RDP loads nothing for an empty rectangle; loadTile now returns for w <= 0 / h <= 0 and loadBlock clamps to the 4 KB TMEM.
- After that fix the soak still froze at the same point, this time with every thread alive: a stall watchdog thread (`stall_watch` in game_glue.c, dumps `STALL: ... g_lock owner/recursion, every game thread's state/queue/eip/stack, the platform thread`, through WriteFile only) showed all eight game threads waiting on their queues and the platform thread inside `runDL` twelve levels deep: a self-referencing display list (the game re-initialising while the renderer still reads the previous task's list) ran the 200000-command guard at every nesting level, i.e. forever. `runDL` now has a per-frame budget of 4M commands (`renderer: display list runaway, frame abandoned` once it trips); the per-vertex `getenv("TUROK_VTXLOG")` it was spinning in is cached.

### Black player-select / join screens (2026-10-09)
- Screens 26 (how many players) and 7 (character select, the portraits + character grid) rendered completely black in every build, although the renderer executed all 162 draws of the frame (the main menu before them was fine, so nobody had screenshotted them). ### Root cause of a class of "mystery" menu bugs: stage-1 optimisation vs the byte-order rewrite (2026-10-10 night)
- Symptom: the random-input fuzzer crashed in the loadout (`func_0042A994`, `h->unk10 = a` through the NULL result of the widget lookup `func_0040ECB0(root, D_800E4F64[i].a.h.h1)`; 3 of 8 runs).  The table entry was `00 00 03 16`, `.a.w` read 0x316 (the `if` matched) but `.a.h.h1` read 0 and `.a.h.h0` read 0x316: the lookup asked for widget id 0.  Cause: the port compiles C -> LLVM IR (stage 1, `-O1`) -> big-endian rewrite of loads/stores (`port/be_ir.py`) -> x86.  Stage-1 optimisation folds memory accesses with the HOST's little-endian layout: the halfword of the union `O04W { s32 w; struct { u16 h0; u16 h1; } h; }` that was already loaded as a word became `lshr i32 %w, 16` (LE: h1 is the high half), but after the rewrite the word holds the guest value where `h1` (offset 2) is the LOW half.  Everything the optimiser derives from the memory layout (union halves, narrowing of loaded words, merging of adjacent loads/stores, store-to-load forwarding across widths, SROA of byte/halfword arrays) is wrong after the rewrite; at `-O0` clang emits one load per access and nothing is folded.
- The earlier hand-written NULL guards (`port/overrides/func_0040E958.c`, `func_0040E9D0.c`) and the "func_00427690 reads a NULL object at -O1" finding (answered with `-O0` for every mode=sn source) were this hazard in other shapes.
- Fix: `build_clang.stage1_flags()`: guest code (`ov_`, `func_`, `lu_`, `nm_`, `ar_` objects) is compiled with `-O1 -Xclang -disable-llvm-passes` (IR as at -O1 but no LLVM pass runs), so nothing is folded before the rewrite, and the second stage (`zig cc -O1` on the rewritten IR, where memory is consistently byte-swapped) does the optimising.  Native helpers (`nt_`, `zd_`: the RNC decoder) keep `-O1`.  `PORT_O1_STAGE1=1` restores the old behaviour, `PORT_NOPASS=name,name` applies it per source, `PORT_O0=name,name` / the mode=sn list still force `-O0` (+ UBSan).  A full `python port/build_clang.py --all` is needed after the change (~10 min).
- `port/softfault.c` stays as the safety net for the remaining NULL-page accesses.

### Controller Pak: a virtual memory card (2026-10-10 night)
The pak is emulated at the serial-interface level: the game's own libultra pak code (id/index checks, repair, note table, allocation, read/write, delete) runs unmodified against a virtual Joybus device, the "pak is always absent" overrides are gone, and the saves are ordinary 32 KiB `.mpk` files (Project64 compatible).  New code: `port/pak.c` (device + file backend), `port/pak_os.c` (the libultra pieces that had no usable code), `tools/pak_tool.py`, tests in `port/paktest.ps1` / `port/tests/`; the only edits of existing files are a few lines in `port/os_shim.c` (and thin wrappers in `port/overrides/osPfsInitPak.c` / `osPfsIsPlug.c`).  User-facing summary: `saves/README.txt`, sample settings `saves/turok_pak.ini.sample`.

- **What the game does with the pak.**  1 PLAYER TRIALS opens the pak screen (UI screen 19): osPfsInitPak (id and index-table checks, repair of the primary copies from the backups), the player list (`osPfsNumFiles` / `osPfsFileState`, "SELECTED / NEEDED 7 / FREE n"), CREATE PLAYER (osPfsAllocateFile + osPfsReadWriteFile, then LOAD reads the data back), DAMAGED CONTROLLER PAK (ATTEMPT REPAIR = osPfsChecker, RETRY, CONTINUE WITHOUT SAVING), NO CONTROLLER PAK FOUND; the main menu's CONTROLLER PAK screen deletes players (osPfsDeleteFile).  A player is one note: game code `NRWE`, publisher `51`, name `RAGE WARS` with the player's name as extension, 7 pages (1792 bytes); the game needs 7 free pages and a free one of the 16 note slots.  Right after the title screen appears the game initialises the pak (`osPfsInitPak`, which creates the file of that port) and the rumble (`func_00264268`: osMotorInit, osMotorStop twice, osMotorInit; sets the controller's "rumble present" flag) of every connected pad, and from then on a per-frame update (`func_00264124`) calls osMotorStop every frame, or osMotorStart for a fraction of the frames (a pulse accumulator) while an effect is running, once the rumble pak was detected; the rumble prompt (screen 25, "THIS GAME IS RUMBLE PAK COMPATIBLE ...") precedes a level.
- **Emulation level.**  `__osSiRawStartDma` (the shim's former no-op) hands every 64-byte PIF RAM transfer to `pak_si_dma()`: a write DMA copies the buffer in and, when the control byte (offset 63) has bit 0 set, parses the command list (`0x00` skip channel, `0xFF` no-op, `0xFE` end, `0xFD` reset, otherwise a handshake `tx rx data..`); a read DMA executes the parsed list (channel 4 first, channel 0 last, like the PIF) and copies the buffer back with the PIF's error flags in the top bits of each rx byte (`0x80` no device, `0x40` timeout).  Commands per controller: `0x00` / `0xFF` identify (reply `05 00` + status), `0x01` read buttons (zeros: the shim keeps the HLE input), `0x02` / `0x03` read / write 32 bytes of accessory memory with the 5-bit address CRC (x^5+x^4+x^2+1) and the CRC-8 (0x85) of the data.  The status byte is `1` accessory present, `2` none, `3` new accessory since the last identify, `+4` address CRC error in the previous command; a freshly inserted accessory ignores accesses until it has been identified, so libultra reports PFS_ERR_NEW_PACK after a hot swap.  `osContInit` / `osContGetQuery` fill `OSContStatus.status` from the same model (one source of truth).  Channel 4 (cartridge EEPROM) stays unpopulated.  Memory pak = 32 KiB SRAM (blocks 0x0000-0x7FFF; 0x8000+ reads 0 and ignores writes, so the SDK's bank probe sees one bank and the rumble probe fails with PFS_ERR_DEVICE); rumble pak = identification register 0x8000-0xBFFF (reads 0x80 once 0x80 was written, i.e. libultra's probe succeeds) and motor register 0xC000-0xFFFF (bit 0 on/off).  A SI transfer costs about 0.5 us on the host (2760 transfers in a create-player session, the longest 0.64 ms).
- **Replaced libultra code and why.**  Everything else comes from the ROM: `osPfsInitPak` (the recompiled twin `func_00447BB0`), osPfsChecker, osPfsAllocateFile, osPfsReadWriteFile, osPfsDeleteFile, osPfsFreeBlocks, `__osCheckPackId`, `__osPfsRWInode`, `__osPfsSelectBank`, `__osPfsGetStatus` ... are the game's own code (recompiled twins or ported C, as already linked).  `port/pak_os.c` supplies only what had no usable code, each a line-by-line transliteration of the disassembled ROM function that keeps the original buffers at their original addresses (`__osPfsPifRam` 0x80154110, `__osContPifRam`, `__osMotorStartData`, ...) so the game's other code sees what it would on a console: `__osContRamRead` / `__osContRamWrite` / `__osContGetInitData` (the MIPS code moves the 40-byte Joybus packets with lwl/lwr/swl/swr, which the recompiler does not translate: they were UNIMPLEMENTED stubs), `osMotorInit` / `osMotorStart` / `osMotorStop` (only host shims existed, "no rumble pak" everywhere) and `osPfsIsPlug` (not called by the game; standard routine).  `osPfsInitPak` / `osPfsIsPlug` in `port/overrides` are thin wrappers now, so a rebuild of the overrides cannot bring the "return 1" stubs back (`pak_os.c` defines the same symbols and wins at link time; both files can be deleted).
- **ABI trap found on the way: `corrupted()`.**  The first player note the game wrote was zeroed a moment later: `osPfsChecker` declared every note of a perfectly valid pak "corrupted" and deleted it.  The checker's helper `corrupted(pfs, fpage, cache)` takes the page link `fpage` (`__OSInodeUnit`, a 2-byte union) BY VALUE; the recompiled checker passes it like MIPS o32 does (halfword in the high 16 bits of a register image), the ported C `corrupted()` expects the x86 struct image and read page 0 / bank 0 for every link.  `pak_os.c` therefore serves the symbol `corrupted` from the recompiled twin of the same ROM code (`func_00448308`, same convention; its only caller is the recompiled checker).  Found with the diagnostic `TUROK_PAKTWIN=all | name,name` (patches the named ported-C pak functions to jump to their recompiled twins; A/B tests narrow it down).  Same family as the by-value struct notes in "Recompiler lessons".
- **Files.**  Default folder `<exe folder>\saves` (a dev build runs from `port\build`, so its paks appear in `port\build\saves`: keep them out of git; `saves\README.txt` and `saves\turok_pak.ini.sample` are the files to ship); port n uses `<name>_Cont_<n>.mpk` with the ROM's internal title as `<name>` (`Turok; Rage Wars`: ':' -> ';' and '/' '\' -> '-', Project64 2.x/3.x's rule), e.g. `Turok; Rage Wars_Cont_1.mpk`.  Lookup order for port n: explicit `TUROK_PAKn` / ini `pakn` (`file#k` = pak k of a multi-pak file) > a Project64 Save folder (`TUROK_PJ64_SAVE` / ini `pj64_save`: `<name>_Cont_<n>.mpk` there or in its `<name>-<md5>` per-game folders (Project64's "unique save folders"), then `<name>.mpk` (Project64 1.6 / Jabo, mupen64plus: for port 1, or pak n of a 4-in-1 file) and prefix matches) > `<savedir>\<name>_Cont_<n>.mpk`.  Containers: raw 32768 bytes (`.mpk`, `.mem`), DexDrive `.n64` (0x1040-byte header `123-456-STD`, pak at 0x1040), N x 32 KiB (mupen64plus 4-in-1: port n = pak n), mupen64plus-next `.srm` (0x48800: 4 paks at 0x800), 32 KiB plus appended data (MPK Manager comments); the whole file stays in memory and is written back whole, so headers, the other paks of a multi-pak file and trailers survive untouched.  A missing or empty file becomes a freshly FORMATTED pak (labels, four id blocks with a random serial, both index tables, empty note table: the structure of a freshly formatted card, valid for the game's checker and for `pak_tool.py`; formatted rather than blank so that the player does not have to run a format, and the checker does not report a "damaged" card on first start); an all-0x00 / all-0xFF file counts as unformatted and is formatted; a short file is padded in memory (the checker sees a damaged pak) and the 100-odd-byte original is kept as `<file>.orig` before the game's repair rewrites it; a damaged 32 KiB file is also copied to `.orig` once before its first write.
- **Write-back.**  Changes are marked dirty and written by a low-priority thread 300 ms after the last change (never later than 8 x that + 1 s of continuous writing), as temp file + `MoveFileEx(REPLACE_EXISTING|WRITE_THROUGH)` in the same folder, so a crash leaves the old or the new file, never half of one.  Flush points: debounce, `flush` command, process exit (`atexit`), and a vectored exception handler that writes pending paks before an unresolved fatal exception (try-lock only, never blocks).  A hard kill loses at most the last 300 ms.  Read-only files, files another process holds open, oversized (> 16 MiB) files, unreadable files and an uncreatable save folder give a session-only pak (log line says `NOT SAVED` and why) and never touch the file; a failed write is retried with back-off.  A file changed on disk behind the game's back is picked up when the pak is taken out and put back in (hot swap, `reload`); while it sits in the port the game's copy wins.
- **Configuration** (environment variable > `turok_pak.ini` next to the exe, `TUROK_PAK_INI=<file>` > default; `saves/turok_pak.ini.sample` documents all keys): `TUROK_PAK=0|1` / `enabled` (master switch, 0 = old behaviour, nothing plugged in; the oracle runs default to 0), `TUROK_SAVEDIR` / `savedir`, `TUROK_PAK1..4` / `pak1..4`, `TUROK_PJ64_SAVE` / `pj64_save`, `TUROK_PAK1_TYPE..4` / `port1..4` = `none|memory|rumble` (default `memory` in every port; consistent with the status bits osContInit reports), `name`, `TUROK_PAK_DELAY` / `writeback_ms`, `hotkeys`, `TUROK_PAKLOG=1` / `log` (every accessory transaction).  `TUROK_PAKSYNC=1` logs `pak: idle` when the SI has been quiet for 250 ms (test scripts wait for it).  A port whose pad is not connected answers "no device", whatever its type.
- **Runtime control.**  Ctrl+F5..F8 pull out / push in a memory pak in port 1..4, Ctrl+Shift+F5..F8 a rumble pak (window focused); the same through a control file `port_pak.txt` in the working directory, polled and deleted by the game: `insert <port> [memory|rumble]`, `remove <port>`, `reload <port>` (re-read the file), `format <port>`, `flush`, `status`.  After an insert the next identify reports status 3, so the game's own "new pak" handling runs.  A rumble pak in port 1 makes the pak screens of that port say NO CONTROLLER PAK FOUND (a rumble pak is not a memory pak) and, with an XInput pad, vibrates it while the game's motor register is on.
- **Game behaviours worth knowing.**  Deleting the last player of a pak makes the game write a fresh default player at once (`RAGE WARS.B` in the delete test, whose synthetic foreign notes already use the extension `A`: see the naming rule below), so a pak never stays without one; a pak with fewer than 7 free pages or without a free note slot makes CREATE PLAYER refuse (`.\port\paktest.ps1 -Test full`: 6 free pages refuse, 7 and 8 save); the game names a new player after the first letter that no note of the pak uses as its extension, whatever the note's game (the dialog says "CREATE NEW PLAYER A", but next to a foreign `SPEED RACER.A` the note is written as `RAGE WARS.B`); pulling the pak out before the pak screen opens gives NO CONTROLLER PAK FOUND (RETRY / DONE), pushing it in and RETRY lists the saved players (the status-3 "new accessory" report is consumed by the game's own, continuous `osContGetQuery` poll first; the pak screens only look at the pak when they open or on RETRY, so pulling it out while the player list is shown changes nothing on screen); damaged images: the id block copies and the index table copies are repaired by the game on first contact (`id-primary`, `fat-primary`, `fat-sum`, `fat-both` end valid), `id-all` (every id copy bad) shows DAMAGED CONTROLLER PAK until ATTEMPT REPAIR, broken note chains / loops are removed by the checker, cross-linked notes are left alone until a user action touches them, an all-zero file is simply formatted; foreign notes with intact chains are never touched (byte-identical, tested through create, delete and repair).
- **Tools and tests.**  `python tools\pak_tool.py info|create|insert|extract|delete|corrupt|diff|same-notes|fake|selftest` is an independent implementation of the format (CRCs, id blocks, index tables, note table, cross-link / loop / bad-link checks, all container types) used to validate what the game produced; `port\tests\pak_selftest.ps1` builds and runs a host self test (CRCs, PIF engine, devices, `__osContRam*` / motor sequences, file backend, 215 checks); `.\port\paktest.ps1 [-Test name,..] [-List]` drives the real game with scripted input (`port\pakpress.ps1`, a copy of pressfile.ps1 that only touches the exe named in `port\build\latest_exe.txt`, so name it `pakw_*.exe` with `tools\linkpak.ps1`: the older scripts kill every `turok_*` process of the machine) and checks the produced files with the tool.  Tests (`-List`): `selftest pytool lvl-nopak lvl-pak create persist delete exit-flush files fuzz skipmenu mptour damaged foreign full containers hotswap config firstrun pj64 format ports4 crash-flush match` (about 10-12 minutes for all on a quiet machine, the scripts run the game at 10x), optional `soak timing`.  They synchronise on screen ids and the `pak: idle` marker (`TUROK_PAKSYNC=1`) rather than fixed times, but they are still blind scripted menus: on a loaded host rerun a failing scenario alone before suspecting the code.  Measured: 60 fps at 1x with and without the pak (14 / 15 samples of 5 s, minimum 60).
- **Not done / limits.**  Multi-bank (>32 KiB) paks are not emulated (the SDK's bank probe sees one bank; paks of other games with several banks load but only bank 0 is visible); no GUI for managing paks (use `pak_tool.py` or Project64's tools); two game instances (or the game and an emulator) using the same pak file at the same time are not coordinated (each replaces the file atomically with its own copy: the last writer wins); Transfer Pak, VRU, EEPROM and Joybus RTC are not emulated; the rumble motor was not seen ON in the game (next bullet).
- **Rumble in the game: handshake verified, vibration not seen.**  With a rumble pak in port 1 the game's rumble init succeeds (`rumble pak unlocked` in the `TUROK_PAKLOG=1` log), `TUROK_WATCH=8010F3F4` shows the controller's rumble-enable word (`+0xCC` of the controller object at 0x8010F328 + 0x224 * port) going 0 -> 1 when the level is set up, and the per-frame update writes the motor-off register every frame (12000 writes in a level run); but no vibration was ever requested: the intensity (`+0xD0`, `TUROK_WATCH=8010F3F8`) stayed 0, and neither the global effect list `D_8010EC90` nor the player's own list (controller `+0x140`) ever allocated a node (`TUROK_WATCH=8010EC90` / `8010F468`).  Rumble effects are created by the positional-sound code (`func_0028CE70` -> `func_00285B34`) for sounds that have a rumble entry, and none occurred in ~70 s of walking, firing and weapon switching in the 1-player trial or in a 10-minute match against a bot.  Path to that match (`.\port\paktest.ps1 -Test match` runs it with a 1-minute limit): MULTIPLAYER, HOW MANY PLAYERS 1, character select A, loadout: stick down 5 x then A on the green OK, mission GAUNTLET A, match options START GAME A (1 bot, NOVICE), rumble prompt A, intro camera A; the bot never engaged (0 frags / 0 deaths / 0% hits on the results screen).  So the vibration path (`osMotorStart/Stop` -> pak motor state `pak_rumble_get` -> `input_motor_set` -> the gamepad assigned to the port, see "Input") is verified at the device level (self test) only; a match in which somebody gets hurt or an explosion goes off is the way to see it end to end.  The 2-player loadout is the same (each pad: stick down, A on OK), the blind script did not get through it.
- **Regeneration traps.**  `port\linkgame.ps1` compiles every `port\*.c`, so `pak.c` / `pak_os.c` need no build change; `pak_os.c` refers to `func_00447BB0` (twin of osPfsInitPak), `func_00448308` (twin of `corrupted`) and, for `TUROK_PAKTWIN`, a few more twins and C functions.  If a regeneration replaces those twins by matched C, `func_00447BB0` / `func_00448308` become aliases of C functions named `osPfsInitPak` / `corrupted` that the definitions in `pak_os.c` shadow: `pak_os_init()` detects the loop, logs `pak: WARNING ...` and degrades (no pak / nothing "corrupted") instead of recursing; the fix is to delete `osPfsInitPak` resp. `corrupted` from `pak_os.c` (and the two override wrappers).  `tools\pak_tool.py` and the host self test do not depend on any of it.

## Input: keyboard, mouse, gamepads, `controls.ini` and the mapping program (2026-10-11)
Source layout: `port/input_core.[ch]` (platform independent: N64 controller model, binding sources, controls.ini parser / writer, built-in profiles, the mapping engine; unit tests in `port/config/input_test.c`), `port/input_dev.[ch]` (Windows device layer), `port/input.c` (game integration: assignment, capture, hotkeys, hot reload, rumble shims), `port/config/` (the mapping program `turok_controls.exe`).  Hooks in existing files: `os_shim.c` (`pad_connected` -> `input_port_connected`, `input_poll_begin` / `input_poll_port` in `osContGetReadData`, `osMotorInit/Start/Stop` -> `input_motor_*`; the old `key()` / `xinput_pad` code is dead but left in place) and `win32_main.cpp` (`input_attach(hwnd)` after `CreateWindowA`).

How it works
- **Devices.** Keyboard + mouse: Raw Input on a private thread (hidden sink window, `RIDEV_INPUTSINK`): physical scancodes (so WASD stays under the same fingers on AZERTY / QWERTZ), unaccelerated relative mouse motion, every key transition including taps shorter than a frame (latched until the game polls).  Gamepads: XInput slots 0-3 (rumble) and DirectInput 8 for every other game controller (PS4/PS5 and Logitech D-mode have known layouts, others a heuristic Xbox-style or raw `Pad.Btn5` / `Pad.Axis3+` / `Pad.Hat1Up` numbers); both loaded dynamically from system DLLs, hot-plug by a 1 s scan.  Devices only count while the game window is in front (`background_input = on` lifts that); keys held while the window got the focus are ignored until released.
- **Polling.** `osContGetReadData` takes one snapshot per frame (`input_poll_begin`) and maps it per port (`input_poll_port`); nothing is queued across frames, so the added latency is the game's own one-frame poll.  Scripted input (`port_input*.txt`, `TUROK_AUTOPRESS`, `TUROK_REPLAY`) is merged first and wins: real devices are read for a port only while no scripted input is active on it.  `TUROK_INPUT=0` (and oracle mode) disables the real devices altogether.
- **Players.** `[player1]`..`[player4]` of `controls.ini` list their devices (`keyboard`, `mouse`, `pad:auto`, `xinput:N`, `dinput:N` / `dinput:{guid}` / `dinput:name=...`).  Defaults: player 1 = keyboard + mouse + first free pad, players 2-4 = the next free pads in order.  `osContInit` / `osContGetQuery` report a port as connected when its player has a device assigned and available (player 1 always; `TUROK_PADS=n` keeps forcing ports `< n`).  The keyboard can be shared (profiles `kb_left` / `kb_right`), the mouse and each pad serve one player.  Pads are handed out again when one is plugged in or removed (a pad keeps its player while it stays connected).
- **Mouse look.** The game has no camera input besides the stick, so mouse motion is converted to the stick value that turns the view by the asked angle: the game's turn rate is cubic in the stick value (measured at the default CONTROL STICK sliders: yaw `1.978e-4 * e^3` deg/s, pitch `3.10e-4 * e^3`, `e = |stick| - 3` after the game's dead zone, 90 deg/s at the stick maximum; 1 mouse count = 0.05 deg at sensitivity 1.0, verified end to end: 1000 counts -> 50.0 deg).  Motion that cannot be delivered within one poll interval stays queued up to `mouse_backlog` degrees.  Turn LOOK SPRING off in the game options when playing with the mouse.  The mouse is captured (hidden, clipped to the client area) while a level is running (`mouse_capture = auto`: state 13 with only the HUD layer on the UI stack in a session started through the menus, so attract demos do not capture it); in menus it works as buttons / wheel only.
- **Rumble.** The virtual Controller Pak (see above) decides whether a rumble pak is plugged into a port: `osMotorInit` runs the game's real libultra sequence over the virtual PIF and succeeds only when the port's accessory is a rumble pak (default `memory`: no rumble until `TUROK_PAK1_TYPE=rumble`, `port1 = rumble` in `turok_pak.ini` or Ctrl+Shift+F5..F8; a port holds ONE accessory, as on the console).  When it succeeds, `osMotorStart/Stop` set the pak's motor state and `input_motor_set` (port/input.c) drives the motors of the gamepad assigned to that port (XInput pad with rumble support), smoothed because the game pulse-width-modulates them; a rumble pak in a port whose player has no such pad is silent.  `rumble = off` in `[general]` of `controls.ini` silences the pads, `rumble_strength` scales them.  The pak layer's own `XInputSetState(port)` code and its `xinput_rumble` key are gone: an XInput slot number and a game port number are different things once keyboard and gamepad players are mixed.
- **Hotkeys** (game window): `F1` capture / release the mouse, `F2` reload `controls.ini`, `F3` device report to the log, `Esc` releases a captured mouse, otherwise the first press arms "press Esc again to quit" (`esc = quit | ignore` changes that), `Tab` fast-forward as before.  Short notices appear in the window title.
- **Environment.** `TUROK_CONTROLS=path` (default `controls.ini` next to the exe, then the working directory), `TUROK_PADS=n`, `TUROK_INPUT=0`, `TUROK_INPUTLOG=1` (every change of a port's state + poll statistics), `TUROK_FAKEPADS=1` (virtual XInput pads read from `port_fakepad<1-4>.txt`: `buttons-hex lx ly rx ry lt rt`; used by the tests), `TUROK_RUMBLETEST=1` (pulse the motor once after `osMotorInit`).

Design notes, limits and merge notes (input)
- **Why these APIs.** Raw Input: layout independent scancodes, unaccelerated relative motion, every transition, no dependence on the game window's message loop (`GetAsyncKeyState`, used by the old code, is none of that and not focus aware).  XInput: the standard for Xbox-compatible pads incl. vibration, 4 slots = 4 players.  DirectInput 8: part of every Windows, any HID game controller without report-descriptor parsing (XInput devices that it also lists are filtered with the documented `IG_` test).  Rejected: Windows.Gaming.Input / GameInput (WinRT / redistributable dependency), raw HID parsing (more code and risk for the same reach), SDL (third-party code).  Only system DLLs; `xinput1_4/1_3/9_1_0.dll` and `dinput8.dll` are loaded dynamically, so `linkgame.ps1` needed no change.
- **Stick details.** The N64 stick range is +-80 and the game subtracts its own dead zone of 3 (`func_00263E1C`), so mouse look sends `n + 3` for a wanted `n`; |stick| > 30 reads as a direction press in the menus (keys give 80).  Pad sticks use a radial dead zone (rescaled), optional curve and sensitivity.  Key diagonals are not normalised (two keys give +-80 on both axes; `key_stick` lowers that).  Wheel ticks become one press each (press / release over two polls).  Contexts `game:` / `menu:` exist because the same button means different things in play and in menus.
- **Errors.** A missing file = defaults; a file unusable at start = defaults; unusable at a hot reload = previous settings kept (the tool may be writing it); a bad line = skipped with `input: <file>:<line>: <message>`.  The writer goes through a temporary file + rename.
- **Limits.** Mouse look goes through the stick: the turn rate is the game's own (90 deg/s yaw at the default CONTROL STICK settings; faster flicks queue up to `mouse_backlog`, the rest is dropped; the game's CONTROL STICK sliders raise the ceiling, not measured), LOOK SPRING must be off, no direct camera injection.  Key names are physical positions of a US keyboard.  All mice are merged into one player's mouse.  DirectInput hot-plug is a 1 s scan, DirectInput pads have no vibration.  The context detection reads fixed guest addresses of the US v1.1 build (`0x80146878` game state, `0x8014D080` UI manager); a mismatch degrades to "unknown" (both context layers live).  The tool has no localisation and its controller picture is mouse-only (the input list is keyboard accessible).
- **Hardware.** No physical gamepad was available when this was written.  XInput / DirectInput are covered by synthetic-state tests (`inpdev_selftest`, unit tests) and by virtual XInput pads (`TUROK_FAKEPADS`); the real `XInputGetState` and all DirectInput calls (enumeration, `DIDATAFORMAT`, polling, the VID/PID layout tables for PS4 / PS5 / Logitech F310 / F710) have never run against a device.  First check with a pad: `turok_controls.exe --devices --out devices.txt` (name, VID/PID, "known" or "guessed" layout), then the live test area of the Player tab; in the game F3 writes `input: pad N: ...` / `input: player P: ...` to the log, `TUROK_INPUTLOG=1` logs every state change.
- **Merge notes (`os_shim.c`).** Three small hunks (`orig\port\os_shim.c` in the input workspace has the pristine file): `pad_connected` / the declarations; `osContGetReadData` (`input_poll_begin()` before the port loop, the old port-1 keyboard block reduced to the `TUROK_AUTOPRESS` part, `xinput_pad` replaced by `if (!(b | x | y)) input_poll_port(i, &b, &x, &y);`); `osMotorInit/Start/Stop`.  A Controller Pak implementation that answers `CONT_CARD_ON` in `osContInit` / `osContGetQuery` touches the same area, and `osMotorInit` is the other half of the "which pak is in the slot" decision: a port must not answer both memory pak and rumble pak.  Suggested rule: `osMotorInit` returns 0 only if `input_motor_init` succeeds and the port's slot is not the virtual Controller Pak's; `rumble = off` makes the shim answer "no pak" always.

## Native keyboard / mouse controls (2026-10-11)
Player report on the first real session: in a 1-player level the character did not walk with W A S D and mouse look "did not really work".  Cause: the game turns each
player's controller into four values in `func_002631D0` (player+0x688 pad output: +0x14 turn rate = (stick x / 80)^3, +0x18 view tilt, +0x1C strafe, +0x20 walk) and the
meaning of the buttons depends on the control style of the game's options (player settings +0x7B): style 0 = stick looks, C up / down walk, C left / right strafe;
style 1 = stick walks and turns, C left / right strafe, C up / down tilt (+0x7C = 1 additionally remaps the buttons through `D_800D0DB0`, +0x7D = look spring).  The
`kbm_fps` layout assumed style 0, so in style 1 W tilted the view instead of walking.  `func_002231B0` applies the values (yaw: actor+0x6C radians, eased towards
`ang + turn * 80 * tbl[0]` degrees; tilt: player+0x724 radians, eased towards `-tilt * 80 * 0.716 * tbl[4|5]` degrees, i.e. +-90 deg with the walking table
`D_800CE7E4`), so mouse look through the stick was limited to the stick's top turn rate.
Now (`native_controls = on`, default): `port/overrides/func_002631D0.c` and `port/overrides/func_002231B0.c` are the matched C plus a hook into `port/input.c`
(`input_native_active(port)`, `input_native_get(port, what)`).  In free play the mouse player's motion goes to the view directly (yaw += degrees, tilt set to an exact
angle, both 1:1 with MOUSE_DEG_PER_COUNT x sensitivity, `mouse_invert_y` honoured), and the C-button inputs of a keyboard / mouse player are taken out of the pad data
the game sees and become walk / strafe values (style independent).  The view tilt is kept by the mouse in every style (the look spring and the style-1 C-button tilt /
auto-centring would pull it back each frame); a pad stick still tilts in style 0.  Menus and the attract demos are unchanged (context check as before), and
`native_controls = off` restores the stick emulation.  Not yet tested in the game (written in a session without a Windows build): rebuild with `python port\regen.py`.

## Collision: actors walked through walls (2026-10-11)
- **Symptom.**  Once actors could move (Game Speed seed, see game_glue.c), the player walked straight through walls and out of the level at constant height (`.\port\walltest.ps1`: boot to the 1-player trial, hold C-up in steps, print the camera position after each step; before the fix the position moved ~2,180 units per 4 s step in a straight line for 20,000 units, after it the player stops at a wall).
- **Cause.**  Every actor state's collision options (the `arg4` flags word of `func_00243A80`: floor drop 0x40000, region tracking 0x80000, gravity 0x200, ...) live in BSS profiles at 0x80103FF0..0x80104460.  At boot `func_0023EDF0` copies them from the template table `D_44B4A0`, a data blob INSIDE overlay A's code range (ROM 0x1B94A0, `asm/1B94A0.s`).  The port runs the overlay code natively and only loaded the overlay's data tail (ROM 0x1BCDA0..), so the template read as zeros, the copy loop stopped at its first NULL entry and every profile stayed 0: no wall query could hit, no floor, no region (`room`/`collision` of every actor stayed 0/NULL).  The second blob in that range (`D_44BDD0`, ROM 0x1B9DD0, handed on by `func_0026AC38`) was missing the same way.  `load_guest_data` now copies both blobs.
- **How it was found.**  Recompiling the whole collision module as twins changed nothing (so not a codegen bug); a logging copy of `func_00243A80` showed `*arg4 == 0`, `room 0`, `collision NULL` for every actor; `TUROK_WATCH` showed nothing ever writes the flags word; then **ground truth from the real game**: a private copy of Project64 4.0 (debugger + interpreter core enabled in its own `Config/Project64.cfg`, a JS script in `Scripts/` with `events.onwrite(new AddressRange(..))` / `events.onpidma` / `mem.u32`, autorun via `[Debugger] Autorun Scripts=`), started with the ROM on the command line, logged the writer (`pc=0023EE74..0023EEB0`, 3.7 s after boot) and the values.  After the fix the port's profiles 0x80104030..0x801041D0 equal the emulator's word for word.  This technique (write watchpoints on the real code path, no input needed thanks to the attract demos) is the quickest oracle for any "this RAM should not be zero" question.

## Gameplay: health 265 then dead, silent weapons (2026-10-12)
Both came from float values going NaN; the damage of an area effect is `(s32)(dmg * NaN)` = INT_MIN on x86 (the MIPS conversion would not even run: the
game never makes these NaNs), so the health went to 0x4CCD... (shown as 265) and the player died; the weapon's fire sounds were placed at a NaN position.
Traced with `TUROK_HWWATCH=<addr>` (x86 debug-register write watchpoint in game_glue.c, logs every NaN store with its writer and a backtrace;
`TUROK_HWWATCH_ALL=1` logs every store): area damage <- animation-event position (func_002476B8) <- the player's weapon matrix (func_0022F5D0)
<- the view camera's quaternion (func_002349B0) <- the camera yaw (func_00220A5C) <- the player's facing angle, written NaN by the native mouse look.
- **Native controls drove the bots.**  The mouse-look / walk overrides (func_002231B0, func_002631D0) took the port number from the controller object's byte;
  bots carry their own AI controller (e.g. 0x8010EEB8) whose byte reads 0, so the mouse turned the bots too.  `port_human_slot()` (port/input.c) accepts only the
  real controller slots 0x8010F328 + 0x224 * n.
- **x87 stack leaks.**  32-bit x86 returns float / double in st(0).  A call through a prototype that says `void` never pops it; after eight leaks every float
  result is the indefinite NaN FFC00000 - which then appears anywhere (bot angle, player angle, camera), and moves with unrelated code changes.  The AI path code
  (func_0021111C / 00211470 / 00211A7C / 00212088) called the float function func_00209308 as void, so the leaks started once the AI ran.  Also fixed:
  func_00272768 (func_00209948), func_002745D4 (func_00284844), func_002A28CC (f64, overlay A), func_0024D388 (a draft).  Prototype-only changes, ROM still
  byte-identical.  `python wip/scan_fpret.py` lists every definition / prototype pair whose float-ness differs (the `ar_` twins and `zd_dt_table.c` lines are not
  calls through the wrong type); game_glue.c checks the FPU tag word on every state-dispatcher call and logs `x87: N register(s) left on the FPU stack` with a trace
  (then empties it), so a leak through a function pointer shows up at run time; `TUROK_X87ENTRY=1` checks at every function entry (the
  -finstrument-functions hook) and names the exact call site of the leak.  That found the last one: overlay A's texture loader
  func_004106F4 called func_002A28CC (f64) under its alias name func_802A18CC_de as void; wip/scan_fpret.py resolves alias names
  through port/gen/alias.rsp now.
- **Struct-by-value arguments.**  clang (x86-windows-msvc) passes a struct with only 32-bit fields as separate native scalars and any other struct as a `byval`
  copy in (big-endian) memory.  The game's sources declare the same 8-byte argument differently on the two sides (`{s32 a, b}` in func_002476B8, `{s16 a, b; s32 c}`
  in the sound handler func_00267324): the fire event's key 0x00000655 arrived as sound id 0.  port/byval_ir.py (run by be_ir.py) turns every byval struct argument
  into one native i32 per word at call sites and definitions, so both conventions pass the same words.  The oracle (Project64 `events.onexec` on the TLB-mapped code
  addresses 0x00257DF4 / 0x00267324 while firing) shows the real game's ids 0x654 / 0x655 / 0x656; the port now starts them.
  Exception: the 11 functions in port/recomp_structargs.txt (40-byte UI context by value) and calls through pointers carrying a 40-byte
  struct keep the old big-endian image, because the recompiler byte-swaps those words for them (mips2c STRUCTARGS); converting them broke

  emptied the main menu (no text), which the pak tests do not look at - check a main-menu screenshot after touching byval_ir.py.  Bisecting aids: `PORT_NO_BYVAL=1`, `PORT_BYVAL_SKIP=<regex,...|INDIRECT>`, `PORT_BYVAL_LOG=<file>`
  (each needs `build_clang.py --all`).
- Test trap: `pressfile.ps1` copies `PF_ENV` into the calling PowerShell's environment, so debug switches (TUROK_HWWATCH ...) set for one
  run leak into later commands of the same shell call (a paktest fuzz "crash" was the watchpoint handler).  One run per shell call, or clear them.
- Verified: health counts down 100 -> 86 -> ... -> 0 and respawns at 100 against the bot (TUROK_HWWATCH_ALL on 0x80692B84), no NaN events, no x87 reports,
