== Workflow tips ==
- Write C directly from the asm + m2c (m2c is good for field offsets and call signatures, bad for control flow).
- wip/ck.ps1 (fn:rom list -> chk with game flags), wip/V.ps1 (variant search wrapper around vq.py; quote the rom as '0x..'
  or PowerShell turns it into an int and vq crashes), wip/side.ps1 (side-by-side with -O2 -mcpu=r4300; try.ps1 uses lu flags!),
  wip/types.py + wip/types_spec.py (sparse struct spec -> include/p2_types.h with explicit padding, avoids offset typos).
- chk masks relocs, so symbol identity is invisible, but the *shape* of address code (lui/addiu base register reuse, `lui $at` +
  lwc1) tells you how globals are declared (see Globals).

== Globals / addressing ==
- Scalar float global used once or twice: `lui $at,%hi(sym); lwc1 $f,%lo(sym)($at)`.  If we declare `extern f32 D[]` and index
  D[1] twice GCC builds `addiu $v0,&D` and uses 0($v0)/4($v0): MISMATCH.  Where the asm says `%hi(D_800CE3E0 + 0x4)`
  the original had a separate scalar (declare `extern f32 D_800CE3E4;` -> matched; same for D_800E28D0/D_800E28D4 as two s32 scalars).
- If the asm builds ONE base register with lui/addiu and then uses it for accesses at 0, +0x44, -0xBCC (func_002549C8), the
  original is a single big extern struct: PoolMgr at D_80103F70 (cnt at +0xBCC, field at +0xC10; D_80104564, D_80104584,
  D_8010510C, D_8010513C, D_80105180 are all inside it).  Declaring `extern PoolMgr D_80103F70;` (struct with padding) and using
  fields reproduced the base-register CSE exactly.  Generalisation: negative/odd offsets from a reg that holds a symbol address
  == members of one big struct/array, not separate globals.
- `lui $v0,%hi(g); lw $v0,%lo(g)($v0)` is the normal scalar integer/pointer global access.
- Arrays of structs: `D[i].field` with stride 16 (func_0023C6AC) compiles to pointer-increment loops; `for (i=0;i<24;i++)` matched at once.
- `if (&sym == 0)` style loop `for (n = &D_80103F88; n != NULL; n = n->next)` compiles with the `beqz` on the constant address (kept by GCC!).

== Idioms: source shape -> codegen ==
- `if (p) return x != 0; return 0;` (positive test, early-return of the false case last) matched where `if (!p) return 0;` did not
  (func_0022BA90).  Similarly `u32 v = flags & 2; return v != 0;` gives `andi; sltu v0,zero,v0` whereas `(flags & 2) != 0` inline
  gives the srl/andi 1 form (func_002458F8).
- A static inline helper returning 1/0 (with `if (c1||c2||c3) return 1; return 0;`) inlined into `if (helper(p)) return 0;` gives the
  `v0 = 0/1; bnez v0` value-materialised pattern with the result in $v0 and forces a reload of p->state afterwards (func_0022C6D4).
  Plain `||` chain in the `if` or a local `s32 r` put the temp in another register.
- Float clamp `t = lim; if (!(x <= t)) t = x;` produced `c.le.s x,lim; bc1t` + `mov.s` (func_0022B68C).  `if (x > t)` produced
  `c.lt.s` (different).  Negating the comparison in source is the way to flip c.lt/c.le + bc1t/bc1f.
- Two branches that both assign 0.0f and share one block (c.lt.s / bc1f / j): write them with a goto into the shared `d = 0` block
  (func_0022DD84).  The natural nested-if form lets GCC CSE the 0.0 into a spare FP register (mismatch).
- switch with a sparse jump table: put the generic `default`-like cases first in source order, and cases that share a tail block
  can have their labels *inside* the earlier `if` body (func_0022EAFC: `case 12: if (x) { case 0: case 18..21: return 1; } return call();`).
  Out-of-range goes to the real `default: return 0`.  Jump table words are plain 0x0022EBxx addresses at ROM = VA - 0x80000000 + 0xC00.
- 3-way if/else-if/else on ints that call the same function with different (ptr,const) pairs: use `switch` (func_0022F504) - the
  if-chain emitted different branch order.
- Independent stores: GCC's scheduler emits them in a different order than source; to get ROM order 0x14,0xC,0x10,0x18,0x8 the
  source order was 0x8,0x14,0xC,0x10,0x18 (i.e. reversed-ish; just try permutations with vq).
- Callee list order does not matter in these small files (no static callee), but declaration style does: K&R `void f();`
  (no prototype) is needed when the ROM does not set up argument registers for a call (func_0024AA08()).
- `return a >= 3 && a < 7;` folds to `(u32)(a-3) < 4`; the ROM keeps two compares, so write nested ifs (func_00232770).
- Loops over `p = p->next` lists with count/sum: for-loop transcriptions matched immediately (6 functions).
- Struct copy `a->seg[i] = *src;` for a 24-byte struct emits the lw t0-t3 / sw / lw t0,t1 / sw sequence: matched.
- memset call args: `memset(o->f1C = blk->data, 0, n << 6)` (assignment inside the call) reproduced the store-in-delay-slot order.

== Unmatched residue (for the next batches) ==
- func_0024B8DC / func_0024B980 (1 word each): ROM has `sllv $a3,$v0,$a2` (shift amount = the register that holds the constant arg 1)
  inside the `idx*24` address computation, we emit `sll $a3,$v0,1`.  Something makes cse reuse the pseudo holding constant 1 as
  shift count; local `one` variables, explicit shifts, casts did not reproduce it.  Probably the same trick as any other `x*3` next to
  a literal-1 argument; worth testing in other functions to learn the trigger.
- func_0022C1D8: pure FP register numbering (two live f32 pseudos swapped); func_0023C77C: pure callee-saved swap (s0/s1).
  Both are allocation-priority/pseudo-order effects; permuting local declaration order and expression grouping did not flip them.

TOOLING
- tools/try.ps1 / lu_ud.sh use the libultra default flags (-O3 -fforce-addr) unless env FLAGS is set: for game code its
  side-by-side output is MISLEADING.  I use wip/side.sh <fn> [file] which runs lu_ud.sh with FLAGS='-O2 -mcpu=r4300'
  (then tools/lu_side.py).  wip/mk.sh <fn...> builds the chk list (wip/out/<fn>.c or wip/hard) and runs chk.
- vtry.py ranks by "first differing word"; a result "1000000 words" is either EXACT or a COMPILE FAIL (C89: no declarations
  after statements!).  Check the final line ("best file ... EXACT") or run chk.
- vq/vtry write wip_list.txt in the project root and keep stale wip/_v_*.c files: rm wip/_v_*.c between searches.

ARGUMENT PASSING (biggest win of the batch: unlocks many "weird" prologues)
- A `sw $aN, home($sp)` of an incoming arg register in the prologue + a `lw $aN, home($sp)` right before a call means a
  STRUCT passed by value that begins in a register (usually a Vec3 {f32 x,y,z} starting at a1/a2/a3: remaining words are on
  the stack).  Declare the parameter as a struct (P3Vec3) in both function and callee prototype; gcc copies the stack part
  of the struct to the outgoing area with lw/sw (this explains "stack args reloaded and re-stored in pairs").
  Float values passed as plain f32 after an int arg are in INT regs (mtc1 a1,...) - declare f32 params, no casts.
- Plain stack int args are loaded at function ENTRY only when the pseudo is multiply set/used; if the ROM loads a stack arg
  early but the C loads it late, add a local copy and a dead later assignment (func_00268864: `k = e; ... k = 0;`).
- `sw v0,16($sp); lwc1 f0,16($sp)` after a call returning s32 = bit-pun of an int return into a float:
  `s32 tmp = f(); x = *(f32*)&tmp;` (a union gets optimised into a direct mtc1/no stack trip and does NOT match).
- (s16)param passed on to a callee taking s16: `sll 16; sra 16` appears at the call, the raw register is stored elsewhere:
  make the parameter s32 in your function and s16 in the callee prototype.

GLOBALS
- A global array/struct accessed several times (`extern s32 D_x[]; D_x[0]` twice) keeps its address (lui+addiu) in one reg,
  while a scalar `extern s32 D_x` is lui/lw, lui/sw each time.  func_0025E2F4: use the array form to get `addiu $v1,$v1,%lo`.
- A symbol referenced as `D_800C9490` and `D_800C9490 + 4` in two separate lui/lwc1 pairs (each with its own lui $at) =
  two separate scalar globals D_800C9490 / D_800C9494 (an array would CSE the base).  Declare them as two scalars.
- Float/double literal pools: u32->f32 conversion goes u32->f64 (cvt.d.w + add 2^32 literal if negative) -> cvt.s.d; the
  literal (ro=0x...:8) is reported by chk.  Casting a u32 to f32 reproduces this.
- Tables of 4 pads etc. (D_8010F310[4], D_8010FC28[4], D_8010FBF0[4]) are separate s32 arrays; loops indexed `D[i]` compile
  to walking pointers anyway (3 ptr + counter), so write array indexing, not pointer walking.

CODEGEN <-> SOURCE PATTERNS
- Local `k = i*2` reused later gave a different register assignment than writing `i*2` and `i*2+1` inline (CSE does the
  rest): prefer repeating the expression (func_0025D370).
- Float min/max: `box[0] = pt[0] <= box[0] ? pt[0] : box[0]` generated the INVERTED compare (c.le swapped, bc1tl);
  the ROM form came from `!(p[0] <= box[0]) ? box[0] : p[0]`.  For a loop over 12-byte points use `p = pt + i*3`
  inside a `for (i...)` (the `pt++` form let gcc strength-reduce the z access differently).
- A short if-chain returning 1 at the start and in several places with a trailing `x==1||x==4||x==7||x==0xB` test is a
  `switch(kind){case 1: case 4: case 7: case 0xB: return 1;} return 0;` (gcc emits a compare chain for sparse cases, so
  the S flag in targets.txt is not reliable either way).
- Delay-slot filling: if our version has `bnezl` + hoisted store where the ROM has `bnez; nop` and the real first insn of the
  else block is a `lw`, swap the order of the first two statements of that block (func_00279530: `n->prev = l->head;` first).
- if/else shape: when the ROM lays out the "zero everything" case LAST (after the nested ifs), write
  `if (cond) {nested...} else {zero...}` (func_00263C44); writing `if (!cond) {zero} else ...` gives different jumps.
- Struct-local copies: `P3QArr loc; loc.q = a->q;` (copy only the sub-struct, local keeps the unused first word slot so the
  copy lands at sp+4) matched the frame layout of func_00260CBC; `P3QInfo q = a->q` gives sp+0.
- Hoisting of `w[1]` above `if (sh)` needs a named temp `hi = w[1]` before the branch (func_00260CBC).
- Leaf mutex-like code: `u32 mask = __osDisableInt(); if (++l->count != 1) {__osRestoreInt(mask); osRecvMesg(...);} else __osRestoreInt(mask);`
  matched directly (the duplicate __osRestoreInt in both arms is real, not a join).

CODE-BASE STYLE
- Game objects are big structs accessed with raw offsets: pad arrays + named fields are enough; there is no sign of
  bitfields.  Helper wrappers on one global object (D_8010C080: a sound/audio lock object) are 9-insn thunks

- Vector/matrix code: 4x4 f32 row-major, rows 0x10 apart; vec math is spelled out per component, left-to-right sums
  `a*x + b*y + c*z`; mult operand order is (matrix elem * vector elem).  Matches first try with plain expressions.
- libultra-style doubly linked lists with embedded sentinels at +4/+0xD8 of the owner (func_00259938) and counted singly
  linked lists with head/tail/count (func_00279530) are common; sound code uses alSndp* with an ALSndPlayer embedded at +0x84
  of a bank struct.
- Unresolved ordering problems (scheduling / register naming only, instruction mix identical):
  func_00273860 (2 sinf/cosf rotation of matrix rows: ROM loads row-2 elements first, y1/y2 later),

TOOLING (important, affects every function with a struct field offset > 0x7FFF)

  also for loads).  tools/gas_compat.py did not model this (modern gas uses the dest reg for loads and addu at,at,base for stores).
  Patched in my workspace: new `bigoff_re` rule in fix() (copy at wip/out/gas_compat.py; diff is ~15 lines).  With it 00294AC4 and 00292FA4 match.
  Please merge it into the lead's tools/gas_compat.py (and the real build path which uses the same script).
  Source code for such fields is just `*(s32*)((u8*)p + 0x26DC8)` or a struct with a pad[] array; no special trick needed.
- tools/try.ps1 -Side hides relocation differences (it shows `<reloc>` for ours and real insns for ROM, and marks only non-reloc lines).

SOURCE SHAPE -> CODEGEN
- m2c prints `x * K` operand order unreliably; trust the ROM load order. Write `p->f * K` when f is loaded first, `p->f > K`
  instead of `K < p->f` when the variable is loaded before the constant.
- extern const f32 K: gcc CSEs it across calls into a callee-saved fp reg (needed whenever the ROM holds a constant in $fsN).
- Separate fp variables per m2c temp (var_fv0, var_fv0_2 ...) matter for register numbers; a shared temp changed fp regs.
- Cross-jumping explains many "weird" layouts: write the call twice (once per arm), or a direct store `p->st = K` in every arm of
  an if/else chain (no temp variable); gcc merges the identical tails (shared sw / jal) and fills delay slots with the li.
  A temp variable instead gave li; ...; sw in one place and a different register (a0 vs v0).
- bool result of an inlined predicate: `if (a && b && ...) { call(); ok = 1; } else { ok = 0; }` keeps ok in $v0 (nested ifs with
  repeated ok=0 put it in a0 and leave nop delay slots).
- switch statements: cases emitted in SOURCE order; the compare tree (pivot, <, ==) is generated by gcc. For ROM layouts with
  case blocks in odd order (7,2,1/0x12,default) just write the cases in that order (func_0021D750).
- Calls without argument setup in ROM (arg regs still hold the value) = K&R declaration `s32 f();` and a call with no args.
- sqrtf: gcc expands the builtin inline (sqrt.s + c.eq.s + call fallback). ROM calls sqrtf: declare it through an asm label
  (`f32 b05_sqrtf(f32) __asm__("sqrtf");`) to suppress the builtin.
- struct of 0x38 bytes copied with lw/sw loop: struct of s32 w[14] (u8[] struct gives lwl/lwr).
- Vec3f locals are 16 bytes apart (8 byte alignment); first declared = lowest address; address-taken scalars are placed after
  arrays; spilled pseudos (no free callee-saved reg) become stack slots after them (func_00220EB0 spC0..spCC).
- Struct passed by value (Vec3f / 4-word Quat) in the arg list reproduces the lw/sw copies; f32 args after int args travel in int regs.
- Ternary with two separate fp arms: `(t < 0 ? -t : t) * lim` with `m = t * K0` hoisted into a local BEFORE the if gave the ROM order
  (func_002233CC, func_00224078); `dst = expr` directly in each arm instead of via a temp changed fp reg allocation (func_002233CC).
- `while (0.0f < step) { step = 0.0f; ... }` is the source of the "do {...} while (0.0f<0.0f)" m2c output (func_00220EB0).
- A u16 loaded then sign-extended (lhu+sll+sra) vs lh: keep a local as s32, or s16 temp t = (u16)x + n; v = t.
- value = D[idx] style globals: `gm = D_801462D5` (local) keeps the global in a register across later compares.
- `s32 *tb = D_X; tb[0], tb[-2]` gives one base register for sym and sym-8 accesses.

- In-place accumulate matters for FP register allocation: `up = e->f208; up += x * y;` (one pseudo, add.s f1,f1,f0) matched where
  `up = e->f208 + x * y` gave a different destination register (func_0023B708, func_0023CFD0 `c = d->f14; c *= K;`).

- Two arms that end in identical code are cross-jumped by gcc: write the call TWICE (once per arm).  func_0023C074 (osMapTLB / osUnmapTLB
  in both arms) only matched this way; with a shared `goto unmap` the argument registers differ.  Same for inlined helpers: an inline
  with a single return-statement tail after the if/else produced a post-join store; early `return` per arm reproduced the ROM.
- Inlining: Acclaim used `static inline` helpers (func_0023ED54 body is inlined into 0023E8C4/0023EA34/0023DF60/0023E168; the plane-height
  helper is inlined twice into 00240A88; the ray-vs-plane func_002412C0 into 002413B8).  A static inline in the same .c file reproduces it;
  the helper's own copy is a separate global function in the ROM.
- Non-struct stores/loads and CSE: gcc 2.8.1 does NOT invalidate a cached global scalar load after a store through a struct pointer
  (n->prev = g; if (g) ...) and does not reload node fields after a store to a scalar global.  A BLKmode struct copy (movstrsi) however
  invalidates all cached memory: after `D->v8 = a->v180;` the global `D` is reloaded (func_0023E44C).  Offset-0 stores through a plain
  non-struct pointer (`*(int*)n = ..`) also kill cached global loads, offset-4 ones do not (tested with a tiny harness).
  When the ROM reloads a node field after a store to a global list head, store the global through a struct view
  `((B09List *)&D_80103E20)->head = x` (func_0023CBF8) - but using the global ONLY through that view in many places makes gcc hoist its address.
- Loops: `while (n--)` with n a copy of the count gives `addu v0,v1 ; bnez ; addiu v1,-1`; an up-counting `for` over a pointer
  plus `if (cnt != 0) { i = cnt - 1; do {..} while (i--); }` was needed for func_0023CDC4's count loop.
  `for (i = n - 1; i != -1; i--)` (explicit -1 test) reproduced a `bne s0, -1` back edge in func_002414E4.
- Array decl trick again: `extern B09World D_8011FE88[]; D_8011FE88->count` makes gcc keep the base in a register and walk pointers
  (func_0023F42C, func_00240250); `extern T D[]` plus `D->field` for a flag byte hoisted the base out of the loop (func_00240250).
- One struct object spanning two symbols: D_80103254 (load queue) and D_80103D08 (+0xAB4) are the same global; gcc derives one from the
  other (`addiu a0, s1, -0xAB4`) when both are members of ONE extern struct (func_0023CA14).  A thread block + its stack (D_80103950 = base+0x230)
  likewise.
- Switch with jump table (func_0023E44C): `case 1: case 2: case 3: case 4:` with separate arms and identical tails was enough;
  gcc merges the identical `D->unk14 = -1` tails itself.  chk reports ro=0xC9390:40.
- Float compare operand order controls the load order: `h->t >= m->qcopy.t` loads h first, `m->qcopy.t <= h->t` loads m first.
- Dead stores into a local struct are kept (B09V3 p; p.z = ...; unused later) and give the 0x10 frame of func_0023DDB4 / DA90.
- Struct-copy of an f32 triple `B09V3 n = *(B09V3 *)&q->nx;` gives the lw/lw/lw + sw/sw/sw to the stack that the ROM has; later loads are lwc1 from the stack copy.

- Unlinking a node `l` of a doubly linked list and then using it as `n`: write the unlink on `l`, THEN `n = (T *)l;` (otherwise the
  copy is propagated and the register numbering differs).  Insert-before-head: `n->prev = c->prev; n->next = c; c->prev->next = n; c->prev = n;`
  (load first) matches; the reverse store order gets delay-slot copies.
- Struct by value out of a pointer: `Vec3f *p = &o->pos; f(m, id, *p, 0, -1);` (pointer local) matched; `o->pos` directly did not.
- 12 byte Vec3f cleared as `v.x = v.y = v.z = 0.0f;` gives swc1 z,y,x order like the ROM.
- KEY (mutex layout): the inline counting mutex must be written as two `static inline void SndMgr_Lock(SndMgr *m)` / `SndMgr_Unlock(m)`
  functions (local `SndLock *l = &m->lock; u32 mask = __osDisableInt(); if (++l->count != 1) {__osRestoreInt(mask); osRecvMesg(&l->q,0,1);} else {__osRestoreInt(mask);}`;
  unlock: `if (--l->count != 0) {__osRestoreInt(mask); osSendMesg(&l->q,0,1);} else {...}`).  With CPP macros gcc 2.8 (jump.c) parks the
  out-of-line mutex arms behind the first unconditional jump (an early `return -1;`, a second return, ...) and flips the branch polarity
  (bne to an arm placed at the top of the function); with `static inline` functions the arms stay inline exactly like the ROM.
  Only matters when the function has more than one return; with a single return both forms give the same code.

GENERAL SOURCE-SHAPE LESSONS
- Struct by value: `f(T *p, s32 a, B14W3 w)` gives `sw a2/a3 home slots, lw back` and a struct copy `p->w = w` is lw,lw,lw / sw,sw,sw
  (grouped).  A struct param keeps its home slot and fields are read straight from it (func_002609CC reads `lwc1 0xC($sp)`).
  A struct copy through a block move is opaque to CSE: `B14Tmp l; l.r = r;` (local with an unused first word so the copy lands at sp+4)
  reproduces `copy home -> sp+4, then lw a2,4(sp)` exactly (func_00260BA0, func_00260F18).  Two such temporaries (sp+0 and sp+0x10) appear
  when a by-value struct is passed through an inlined helper.
- Compound assignment keeps ONE pseudo, which decides register reuse: `v >>= sh; hi <<= 32 - sh; v |= hi;` gives `srlv v1,v1,a0 / sllv a1,a1,v0 / or v1,v1,a1`
  (all six bit-reader helpers func_002606E4/002607D8/0026102C/00260DC8/00260E6C/00260BA0 need exactly this); `v = (v >> sh) | (hi << (32 - sh))`
  allocates a fresh register.  Statement ORDER inside (`v >>=` before `hi <<=`) fixes the instruction order too.
- Loop strength reduction decides base registers: indexing (`D->blk[i]`, `p[i + 1]`) lets gcc derive per-array pointer IVs whose initial
  value is created AFTER hoisted constants (func_00261110: `li 0xDEADBEEF` before `move v1,t1`); an explicit pointer variable creates its
  init BEFORE them.  For several arrays at fixed offsets from one global use `B14Mgr *m = D_xxxx;` once (or the array form
  `extern S D_x[]; D_x->field`) so one base register is kept (func_00264D00 / 00264BAC / 00264A40).
- `for (i = 0, s = D_x; i < 4; i++, s++)` (both inits in the for header) vs separate statements changes register numbering (func_00264874);
  a second loop in the same function wants its own variable (func_002648E8: first loop temp regs, second loop callee-saved).
- Two uses of the same `&global` after calls are normally CSE'd into a callee-saved register; the ROM often re-materialises lui/addiu
  (func_00264268).  Inlined helpers (static inline in the original) keep separate expansions: func_00263B14 only matches with
  `static inline s32 b14_lock(s32 flag) {...}` called as `if (b14_lock(0) != 0) {...}` (result tested twice, not merged).
- A `switch` on a u8 gives `lbu; beqz; bltz; slti 4; beqz` (range checks NOT merged into sltiu) -- written as 4 sequential cases
  `case 0: ... case 1: case 2: case 3: ...` (func_00263B14).  Nested ifs `if (x >= 0) { if (x < 4)` were merged by gcc.
- `if (...) return 1;` chains over several [lo, lo+size) address ranges match the `&&` form (`a >= lo && a < lo + size`), with the symbols

- `sw $a3,0xC($sp)` (a3 spilled to its home slot) in a function that does not otherwise need a3 = a 12-byte struct passed by value

  `void f(s32 a, s32 b, s32 c, Vec3f pos) {}`.  A Vec3f beginning in a1 or a2 spills a1..a3 (or a2,a3) the same way.
  The callee call then reloads a3 from the home slot (`lw a3,home($sp)`) and copies the stack part (lw/sw pairs, LAST arg first).
- Further struct params after the Vec3f are 8-byte structs (2 words) read with plain lw/lh/lb from the stack:
  {s16 a,b; s32 c} (lh 0x42/lw 0x44 style), {s32 idx; s32 y}, {s32 a; f32 b}, {s32 a; s16 b; u8 c}, 4 x s16 (2-byte aligned: gcc then
  copies it halfword-wise, so a struct with only s16 members cannot be forwarded by value like the word-aligned ones), 7 x u8 (lbu 0x40..0x46).
